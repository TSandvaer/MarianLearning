## Patterns identified

### Pattern A — Cross-review is materially load-bearing; CI alone would have missed 4+ real bugs.

Four TRUE-POSITIVE bugs caught by review during this window, none of which any existing CI gate would have caught:

1. **PR #287 AC4 fabrication.** Integration test fixture claimed `"How many are left?"` as the subtraction template, but the live canon emitted `"How many?"`. Caught by reviewer via ad-hoc node integration test. If Kevin's Wave-2 dispatch had relied on AC4 as-written, the subtraction-template directive change would have been skipped and the canon would have remained unparseable. CI gate gap: the `two-digit-addsub` focus-node was `locked`, so no test exercise path existed. ([#287 comment 4508745947](https://github.com/TSandvaer/MarianLearning/pull/287#issuecomment-4508745947))
2. **PR #291 NOF #7 chip-floor vs lint-floor divergence.** Reviewer identified that `phantomBorrowTrap` lint accepts `trap ≥ 1`, but Devon's planned Wave-3 chip-range floor of 10 would produce silent downgrade on `correct ∈ {12,13,14,15}` subtraction facts. Forward-risk flag; no CI gate exists for cross-PR contracts. ([#291 comment 4516397071](https://github.com/TSandvaer/MarianLearning/pull/291#issuecomment-4516397071); now closed by PR #297)
3. **PR #290 self-caught fixup `b2806ac`.** `isNearBoundaryNoCross` without `a >= 10` clause made Test 4 trivially-green against the add-to-10 fallback (`4+5=9` satisfied `(a%10)+b===9`). The failing-first contract would have been silently broken — test passed on the wrong tier. Self-caught before review.
4. **PR #292 directive prose factual inaccuracy.** Directive claimed `"current canon ships with all THREE round-ten anchors (20+3, 30+5, 40+2)"` — empirically false (canon had one). Cap logic was correct but the rationale's "current state" anchor was fictional. NEAR-MISS for future directive-writers citing the snapshot. ([#292 comment 4517219286](https://github.com/TSandvaer/MarianLearning/pull/292#issuecomment-4517219286))

All four would have shipped if CI alone gated merge. **The review-catches-real-bugs rate is high (4 in 11 PRs).** This pattern is the strongest single argument for keeping cross-review as a hard gate.

### Pattern B — Cross-persona review routing collapsed; 9/11 PRs reviewed by Thomas/code-review skill instead.

Per `[[feedback_pr_review_routing]]`: Devon reviews Kevin's, Kevin reviews Devon's and Kyle's. In practice this window:

- Devon-persona reviewed only PR #288 + #290 (both Jessica). ✓
- Devon's own PR #287 was reviewed by Thomas/code-review skill, not Kevin. ✗
- Kevin's 6 PRs (#286, #289, #291, #292, #293, #294) all reviewed by Thomas/code-review skill, not Devon. ✗
- Kyle's 2 PRs (#285, #295) reviewed by Thomas/code-review skill, not Devon. ✗

The reviews are substantive (local vitest runs, ad-hoc integration tests, commit-SHA-pinned verification) — quality is high. But the **cross-persona context** intent of the routing (Devon brings rendering-side context to Kevin's planner/lint code; Kevin brings backend rigor to Devon's distractor code) is being substituted by orchestrator-level reviews. **This is a process gap, not a quality gap — but the design rationale of cross-persona routing isn't being exercised.**

### Pattern C — Wrong-state factual claim propagated across 5 artifacts before being fully caught.

The "3 round-ten-anchor facts" canon-state claim originated in Kyle's spec (#285), embedded in the directive (#292), echoed in `compositionLint.ts` code comments at four locations (#291), and surfaced **a fifth time** during this retro turn — Kevin's PR #296 discovered an additional wrong-state-framing instance at `compositionLint.ts:2934-2942` in the `resolveTierBinding` block header ("shipped 3-of-8 round-ten-anchor facts") not covered by ticket `86c9xunvq`.

Propagation chain + cleanup:

- Origin: #285 spec (`design/math/two-digit-addsub-content.md`)
- Embedded: #292 directive prose
- Echoed: #291 compositionLint code comments × 4
- Discovered: #292 review
- Cleanup PRs shipped: #293 (directive), #295 (spec markdown), #296 (compLint code comments × 4 — pending merge)

The empirically-verifiable canon-state claim should have been verified at #285 merge time but wasn't. **The `.claude/docs/planner-and-canon.md` "Directive-prose canon-state claims must be empirically verified" pattern was created AS A RESULT of this incident — not applied to prevent it.**

### Pattern D — Out-of-scope and success-test are the two weakest dimensions in ticket bodies.

Across 11 tickets (scored by Angle 2):

- **OOS dimension:** mean 1.55/2. Absent or implicit in 4/11 (#285, #288 retroactive, #290, #294). All 5 impl tickets (#286, #287, #291/#292, #293) scored 2/2 — implementation authors internalize the discipline; spec and investigation tickets don't.
- **Success-test dimension:** mean 1.55/2. Absent in 2/11 (#285 spec PR, #289 investigation-question ticket). These are structurally different work types but the field was blank.

**Sub-finding:** the 6-dimension rubric collapses different work types. A spec PR's "test" is "spec opens to template," not a vitest assertion. An investigation-question ticket's "test" is "the question is answered in the PR body." These are valid done-signals that the impl-oriented rubric doesn't capture. **Recommendation: add a work-type tag (`impl` / `spec` / `investigation` / `test`) to tickets so the rubric can adapt.**

Pre-template tickets had high variance (range 7-16); post-template tickets compressed to 14-15. Lower variance is itself a healthy signal.

### Pattern E — `[[feedback_progression_e2e_mandatory]]` boundary is too narrow.

The rule names `mastery.ts / focusNode.ts / firstEncounterGate.ts / parentSettings.ts` explicitly. But PR #286 touches `guards.ts` + `progressHistory.ts` — both are in the progression persistence chain (step 3 of the mastery pipeline). The team correctly threaded the needle (failing-first companion shipped as #288 same session), but the rule as written would NOT have flagged #286 as mandatory; it was defense-in-depth. **The rule's named-file list lags the actual progression chain.**

### Pattern F — No CI-enforced vitest gate; vitest is trust-the-author.

Only Playwright is CI-enforced across all 11 PRs (all 11 confirmed green via `gh pr checks`). Vitest is run locally by agents and claimed in PR bodies. Counts (2476, 2499, 2579, 2584, 2591) step plausibly and self-consistently across the window — no evidence of cheating — but the gate is unenforceable. `[[feedback_run_vitest_before_merge]]` is sound but soft. **Adding `npx vitest run` as a CI gate (~3-5 min cost) would close this.**

### Pattern G — Lint-infra split-PR pattern lacks failing-first equivalence.

PR #291 ships lint infra with a deferred marker (`.toBeNull()` on `resolveTierBinding`) — this is the documented split-PR pattern (`testing-and-ci.md §6`). But the binding-activation PR (#292) goes green-on-base → green-on-activation; there is no committed-non-compliant-canon-fails-lint moment establishing "the binding was needed." Jessica's failing-first discipline (5 of 9 tests RED on base before impl) produces a falsifiable evidentiary record; the lint split-PR pattern doesn't. **Recommendation: extend the split-PR pattern to require a `lintBeforeRebake` test fixture that runs the new lint function against the pre-rebake canon and asserts it fails.**

### Pattern H — Author concentration on Kevin (55%); Devon underutilized (9%).

Kevin: 6/11 PRs spanning schema (#286), docs (#289), lint infra 2784 lines (#291), canon rebake + binding (#292), cleanup (#293), test helper (#294). Devon: 1 authored PR (#287). Per `[[feedback_dispatch_density_vs_gate]]`, when CI/Vercel is the gate, fan-out is good — but heavy Kevin-load can become a serialization risk on next-tier dispatch if Wave 5 has parallelizable lint + render tracks. **Recommendation: explicitly assign Devon for the render-side / distractor-class work on Wave 5; keep Kevin on planner / canon-lint side.**

## Recommended orchestration improvements

### Action 1 — Codify cross-persona review routing as a hard gate (HIGH impact)

**Delta:**

- Update `[[feedback_pr_review_routing]]` memory: replace "sponsor only for big decisions + iPad testing; Kevin reviews Devon, Devon reviews Kevin/Kyle" with a stricter "EVERY PR by Kevin/Devon/Kyle MUST receive a cross-persona review via the routing table BEFORE merge. Thomas/code-review skill reviews are SUPPLEMENTARY, not substitutive."
- Update `dispatch-template.md` Merge-Identity block: add explicit step "orchestrator dispatches Devon (or Kevin per routing) for the cross-review immediately after PR-open, before any orchestrator review."
- Update `dispatch-template.md` Done-clause: "Done = PR open with: <artifacts> + cross-persona review dispatched + ClickUp → IN REVIEW."

**Evidence:** Pattern A (4 real bugs caught by review) + Pattern B (9/11 routing-misses).

**Expected payoff:** retains the catch-rate (already high) while exercising the cross-persona context exchange the routing was designed for. Low cost: ~1 extra dispatch per PR.

**Risk:** orchestrator over-dispatches if Devon and Kevin are both backlogged. Mitigated by serialization fallback to code-review skill if both worktrees busy >2hr.

### Action 2 — Add an empirical-canon-state verification gate to spec / directive PRs (MEDIUM impact)

**Delta:**

- Update `[[project_dispatch_contract]]` memory to require: any spec or directive PR whose body makes a claim about "current canon ships X facts of Y" or similar empirically-verifiable canon-state MUST cite a verifying `git grep` or canon JSON read in the PR body.
- Update `dispatch-template.md` Self-Test Report template: add line "Canon-state claims verified: <yes/no/n.a.> via <command/file>" for spec / directive PRs.
- Apply pre-merge: orchestrator checks the gate before merge approval.

**Evidence:** Pattern C (1 wrong-state claim → 5 propagated artifacts → 3 cleanup PRs + 1 still pending). The retro itself caught a 5th unprosecuted instance.

**Expected payoff:** prevents repeated factual-claim propagation. Low cost: a single `git grep` per spec/directive PR.

### Action 3 — Improve ticket OOS + success-test discipline; add work-type tag (MEDIUM impact)

**Delta:**

- Update `[[project_dispatch_contract]]` memory to require: every ticket body MUST include explicit OOS list + named success-test BEFORE dispatch.
- Add `work-type` tag dimension: `impl` / `spec` / `investigation` / `test` (free-text on ClickUp ticket tags). Each work-type has a different success-test shape.
- Update orchestrator brief authoring: refuse to dispatch a ticket with missing OOS or missing success-test; fall back to Matt-flesh-out cycle.

**Evidence:** Pattern D (OOS absent in 4/11 tickets, success-test absent in 2/11). Two of the lowest-scoring tickets (#285, #289) are not bad — they're structurally different work types.

**Expected payoff:** reduces the rubric's false-negatives on spec/investigation tickets; raises the floor on impl tickets.

### Action 4 — Add CI vitest gate (HIGH impact, low cost)

**Delta:**

- Add `npx vitest run` as a CI step in the GitHub Actions workflow that runs Playwright today.
- Estimated cost: ~3-5 min per PR run.

**Evidence:** Pattern F (vitest is trust-the-author; only Playwright is CI-enforced). No cheating observed in this window, but the gate is unenforceable.

**Expected payoff:** closes the "I claimed 2591 but didn't actually run it" failure mode. Hardens future failing-first discipline. Cost is small.

### Action 5 — Extend `[[feedback_progression_e2e_mandatory]]` boundary (LOW impact, very low cost)

**Delta:**

- Update `[[feedback_progression_e2e_mandatory]]` named-file list to include `guards.ts`, `progressHistory.ts`.
- Add a "progression-adjacent" extension clause: any new file in the persistence chain auto-qualifies.

**Evidence:** Pattern E (rule too narrow; #286 only got failing-first because team threaded the needle, not because rule required it).

**Expected payoff:** prevents future near-miss when a different agent doesn't thread the needle.

### Action 6 — Extend lint-infra split-PR pattern with `lintBeforeRebake` failing test (LOW impact, MEDIUM cost)

**Delta:**

- Update `testing-and-ci.md §6` to require: when shipping new lint infra via the split-PR pattern, PR A MUST include a `lintBeforeRebake` test fixture that runs the new lint function against the pre-rebake canon and asserts it fails. PR B then asserts it passes.
- This creates the evidentiary "the binding was needed" moment that the current pattern lacks.

**Evidence:** Pattern G (PR #291 → #292 produced green-on-base → green-on-activation; no falsification record).

**Expected payoff:** parallels Jessica's failing-first discipline for lint infra. Cost is one extra test fixture per lint-infra wave.
